02 / SQLite · data quality

SQL validation checks

The problem: a fictional scheduling export includes provider references, external event IDs, and appointment statuses. Some records don't reconcile.

ChecksOrphaned provider references, duplicate external identifiers, missing references, and conflicting statuses.
Judgment callA mismatch isn't automatically a defect. Confirm the integration's source of truth and the meaning of each status first.

Example query

-- Find appointments linked to missing providers
SELECT a.appointment_id, a.provider_id
FROM appointments AS a
LEFT JOIN providers AS p
  ON a.provider_id = p.provider_id
WHERE p.provider_id IS NULL;

The included script creates a synthetic SQLite dataset in memory and runs four checks. No database server or sensitive records are needed.

03 / Functional QA · accessibility

Rescheduling test plan

The problem: a fictional application lets authorized staff reschedule appointments. The feature appears simple, but a successful click doesn't guarantee both application and integration states agree.

CoverageHappy path, conflicts, permission controls, past-date validation, integration failures, keyboard navigation, and screen-reader feedback.
EvidenceStructured test cases, expected results, a high-severity defect example, and questions for release readiness.

Sample defect structure

Title: UI reports success after external calendar failure
Severity: High

Reproduce:
1. Open an appointment as authorized staff.
2. Choose a different available time.
3. Simulate an external calendar HTTP 503 error.
4. Save and inspect both systems.

Expected: No misleading success confirmation.
Actual: UI confirms success, external state unchanged.

Why it matters: Quality testing should validate what the user sees and what the underlying systems actually committed.
